# Account Context Persistence: Research & Recommendation

**Date:** 2026-02-27
**Status:** Research complete, ready for implementation
**Verdict:** One markdown file per plugin. Zero infrastructure.

---

## The Problem

Every session starts cold. The user has to re-explain which accounts they manage, what their goals are, what changed last time, what's being tested. This kills the "this agent knows me" experience.

## The Solution: `account-profile.md`

One markdown file per plugin at `${CLAUDE_PLUGIN_ROOT}/profile/account-profile.md`. Created by `platform-setup`. Read by every skill at invocation time. Updated by skills and optionally by hooks.

### Why This Works

Three independent research passes converged on this answer:
- Every agent framework (LangChain, CrewAI, AutoGen) that reached production ended up with "structured text file loaded at session start"
- Adspirer's ads-mcp uses STRATEGY.md for the same purpose
- Claude Code's own memory system is just `MEMORY.md` files
- Letta benchmarks show plain filesystem scores 74% on memory tasks, beating vector stores
- For <20 ad accounts, a file is the correct tool for 2+ years of usage

### What Goes In It

| Category | Changes | Persist? | Examples |
|----------|---------|----------|----------|
| Account registry | Rarely | Yes — set once | IDs, names, platforms, campaign count |
| KPI targets | Quarterly | Yes | Target CPA, ROAS, monthly budget |
| Active tests | Weekly | Yes | What's tested, when started, what to measure |
| Watch list | Per session | Yes — auto-updated | Anomalies flagged, trends being monitored |
| User preferences | Stable | Yes — set once | Timezone, alert thresholds, reporting style |
| Decision log | Per session | Yes — append-only | What was decided and why |
| Performance data | Daily | **NEVER** — query fresh | Spend, CTR, CPA, conversions |

The critical insight: **never persist performance data**. It goes stale in hours. Always query fresh via MCP. Persist the human judgment layer — what accounts matter, what the goals are, what's being tested.

### The File

```markdown
# Account Profile
<!-- Auto-generated by platform-setup. Manual edits OK. -->
<!-- Last updated: 2026-02-27 -->

## Accounts
- Google Ads: 123-456-7890 (Acme Corp) — ecommerce, tROAS bidding, 12 campaigns active
- Bing Ads: 98765 (Acme Corp) — mirror of Google, 8 campaigns active

## Targets
- Primary goal: ROAS
- Target ROAS: 4.0x
- Max acceptable CPA: $45
- Monthly budget: $50K Google, $10K Bing

## Active Tests
- [ ] Broad match on non-brand campaigns (started 2/20, measuring CPA impact)
- [ ] New RSA headlines in Campaign X (started 2/24, measuring CTR)

## Watch List
- Campaign Y CPA trending up since 2/22 (flagged by morning-brief)
- Bing impression share dropping in Brand campaigns

## Preferences
- Include all accounts in morning brief
- Flag anything >20% off target
- Timezone: EST

## Decision Log
- 2026-02-26: Paused keyword group Y due to $450/mo waste (waste-detector)
- 2026-02-25: Added "free" as negative across all non-brand campaigns
```

### How It Gets Created

`platform-setup` already runs `list_accounts`. After verification, it writes the Accounts section. KPI targets are left blank for the user to fill (or the agent asks once).

### How Skills Read It

Add to each SKILL.md:

```markdown
### Account Context
Read `${CLAUDE_PLUGIN_ROOT}/profile/account-profile.md` at the start of every run.
If it exists, use known account IDs (skip list_accounts discovery).
Apply KPI targets as anomaly detection thresholds.
Note active tests when interpreting performance shifts.
If it doesn't exist, fall back to list_accounts and suggest running platform-setup.
```

### How It Gets Updated (3 mechanisms, simplest first)

**1. User tells agent directly (always works)**
"My target ROAS is now 5.0x" → agent updates Targets section.

**2. Skills propose updates (semi-automatic)**
Add to each SKILL.md:
```markdown
## Profile Maintenance
After completing analysis, if account-profile.md exists:
1. Update Watch List with new anomalies
2. Update Active Tests if user mentioned testing
3. Append to Decision Log if actions were taken
4. Update "Last updated" date
```

**3. Stop hook (fully automatic, Phase 2)**
A `Stop` hook in `hooks.json` parses `last_assistant_message` for watch-list patterns and appends. Runs async so it doesn't block. Optional enhancement — skip for v1.

### What This Unlocks

**Monday morning, user types "morning brief":**
1. Agent reads profile → knows account IDs, skips discovery (saves 2-4 tool calls)
2. Knows targets → flags "CPA $42 vs $35 target (20% over)" not just "CPA is $42"
3. Knows active tests → "CPA up on Campaign X, but broad match test started 2/20 — expected"
4. Knows Friday's watch items → follows up on flagged CPA trend automatically

**Wednesday, user says "CPA is spiking, investigate":**
- Without profile: "What's the target CPA? Which campaign?"
- With profile: "Campaign Y target is $35. Currently $48, up from $33 avg. Broad match test started 2/20 is likely cause — test ad group has $82 CPA."

## Implementation Plan

### Phase 1 (do now — ~30 min of work)

1. Create `profile/` directory in each plugin
2. Add `profile/` to `.gitignore` (customer-specific data)
3. Add `account-profile.md` template
4. Add "Read profile" step to beginning of each SKILL.md
5. Add "Profile Maintenance" section to morning-brief and waste-detector
6. Modify platform-setup to write initial profile after verification

### Phase 2 (later — if Phase 1 proves out)

7. Add `Stop` hook for automatic watch-list updates
8. Add `SessionStart` hook to inject profile as `additionalContext`
9. Add a `profile-review` skill for periodic cleanup of stale items

### Do Not Do

- Vector databases (Chroma, Zep, Mem0)
- SQLite or any database
- External memory services
- Complex summarization pipelines
- Multiple files per account
- Anything requiring infrastructure beyond the filesystem

---

## Architecture Notes

- File lives inside plugin dir → portable with the plugin
- `.gitignore`'d → customer data never committed
- Human-readable and human-editable → user can fix/override anything
- Each plugin owns its own profile → no cross-plugin dependencies
- Same pattern works for meta-ads (swap CPC targets for CPM, add frequency thresholds)
- Skill-scoped hooks DON'T work for plugins (bug #17688) — use plugin-level hooks.json only
